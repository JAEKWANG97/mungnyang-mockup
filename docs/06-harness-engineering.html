하네스 엔지니어링 적용 총정리

정리일: 2026-06-04
목적: 멍냥우편함을 AI로 기획·디자인·구현할 때, 서비스가 SNS/커뮤니티/랭킹으로 새지 않도록 필요한 하네스를 한 문서로 고정한다.

1. 한 줄 결론

멍냥우편함에 필요한 하네스는 거대한 코딩 자동화 시스템이 아니라 기획-정책-검증 하네스다.

Model  = AI의 능력
Harness = 그 능력이 멍냥우편함의 방향을 벗어나지 않게 만드는 실행 환경

멍냥우편함은 귀여운 동물 사진을 다루기 때문에 자연스럽게 피드, 좋아요, 댓글, 랭킹으로 확장되기 쉽다. 하네스의 역할은 AI가 기능을 더 많이 만들게 하는 것이 아니라, 아침 이메일 우편함이라는 정체성을 계속 지키게 만드는 것이다.

2. 왜 멍냥우편함에 하네스가 필요한가

AI에게 “귀여운 동물 사진 서비스 만들어줘”라고 맡기면 보통 다음 방향으로 흘러간다.

  • 공개 피드
  • 좋아요/인기순
  • 댓글/팔로우
  • 프로필/DM
  • 추천 알고리즘
  • 자동 대량 발송

하지만 멍냥우편함의 핵심 경험은 이것과 반대다.

앱에 오래 머무는 서비스가 아니라, 아침에 작은 귀여움 하나가 조용히 도착하는 서비스.

그래서 AI에게 자유롭게 만들게 하기 전에, 반드시 읽어야 할 문서·금지할 기능·검증 기준·사람 승인 지점을 먼저 고정해야 한다.

3. 멍냥우편함 하네스의 핵심 원칙

원칙 1. 서비스 정체성을 먼저 고정한다

멍냥우편함은 동물 사진 SNS가 아니다.

정의:

SNS 없이, 귀여운 동물 사진을 정기 이메일 우편처럼 받아보고, 댓글 대신 버튼 반응만 남기는 익명 동물 사진 우편 서비스.

AI가 작업할 때 이 정의보다 기능 욕심이 앞서면 안 된다.

원칙 2. MVP 제외 범위를 명시한다

아래 기능은 좋아 보여도 MVP에서는 만들지 않는다.

  • 댓글
  • 팔로우
  • 공개 피드
  • 랭킹
  • DM
  • 실시간 채팅
  • 인기순 추천
  • 무승인 대량 이메일 발송

제외 범위는 단순한 “나중에 하기”가 아니라, 서비스 정체성을 지키는 안전장치다.

원칙 3. 정책을 기능보다 먼저 둔다

사진과 이메일은 정책 없이 만들면 위험하다.

필수 정책:

  • 직접 촬영했거나 사용권이 있는 동물 사진만 허용
  • 모든 사진은 발송 전 운영자 검토
  • 신고된 사진은 임시 숨김 후 운영자 판단
  • 명시적 이메일 수신 동의
  • 모든 이메일에 수신거부 방법 포함
  • 실제 발송 전 미리보기/테스트 발송/사람 승인

원칙 4. 반응은 평가가 아니라 수신 확인에 가깝게 둔다

버튼 반응은 “인기 점수”가 아니라 “잘 받았다”는 가벼운 신호다.

허용 반응 예시:

  • 귀여워요
  • 아침이 좋아졌어요
  • 또 보고 싶어요
  • 웃겼어요
  • 따뜻해요

금지 방향:

  • 자유 댓글
  • 싫어요
  • 공개 좋아요 수
  • 인기순 랭킹
  • 업로드자 경쟁 리더보드

4. 하네스 구성요소

1) 컨텍스트 하네스

AI가 반드시 먼저 읽어야 할 문서를 정한다.

00 프로젝트 홈.md
01 구체 기획안.md
02 최근 AI 하네스 사례 조사.md
04 MVP 범위 확정.md
05 핵심 사용자 흐름.md
06 정책과 검증 기준.md
07 결정 로그.md
AGENTS.md

역할:

  • `AGENTS.md`: AI가 지켜야 할 행동 규칙
  • `MVP 범위`: 무엇을 만들고 만들지 않을지
  • `사용자 흐름`: 수신자/업로드자/운영자 흐름
  • `정책과 검증 기준`: 콘텐츠·이메일·반응·개인정보 원칙
  • `결정 로그`: 흔들릴 수 있는 결정을 기록

2) 실행 하네스

AI는 바로 구현부터 시작하지 않는다.

요청 요약
→ 관련 문서 확인
→ MVP 포함/제외 범위 확인
→ 변경 계획 작성
→ 작은 단위로 작업
→ 검증 기준 확인
→ 결정 로그 갱신

이 순서를 두면 “귀엽게 보이는 기능”이 무심코 추가되는 일을 줄일 수 있다.

3) 정책 하네스

정책 하네스는 기능보다 먼저 검토해야 하는 기준이다.

체크 질문:

  • 이 사진은 직접 촬영 또는 사용권이 있는가?
  • 사람 얼굴이나 개인정보가 중심에 나오지 않는가?
  • 동물 학대, 폭력, 혐오, 선정성 요소가 없는가?
  • 수신 동의와 수신거부가 명확한가?
  • 실제 이메일 발송 전에 사람 승인 지점이 있는가?

4) 검증 하네스

작업 결과는 “괜찮아 보임”이 아니라 기준으로 통과시킨다.

검증 질문:

  • 이 결과물이 SNS처럼 보이지 않는가?
  • 댓글/팔로우/랭킹으로 확장되는 유혹을 만들지 않는가?
  • 수신자는 이메일 하나만으로 경험을 완료할 수 있는가?
  • 업로드자는 평가 경쟁을 느끼지 않는가?
  • 운영자는 발송 전 통제권을 갖는가?
  • 신고/숨김/수신거부 흐름이 존재하는가?

5) 사람 승인 하네스

아래 작업은 AI가 단독으로 확정하거나 실행하지 않는다.

  • 실제 이메일 발송
  • 외부 메일 API 연동
  • 실제 사용자 이메일 저장/삭제
  • 이미지 자동 삭제 정책 확정
  • 개인정보 처리 방식 변경
  • 공개 배포
  • 비용 발생 서비스 연동

AI는 초안, mock, 체크리스트까지만 만들고 최종 실행은 사람 승인을 거친다.

5. 멍냥우편함 문서 세트

현재 멍냥우편함은 다음 문서 세트를 기준으로 움직인다.

이 문서 세트의 목적은 문서를 많이 만드는 것이 아니라, AI와 사람이 같은 기준으로 프로젝트를 판단하게 만드는 것이다.

6. 실제 작업에 적용하는 방법

기획 작업을 시킬 때

멍냥우편함 문서를 먼저 읽고, 이 아이디어가 SNS화/랭킹화/댓글화 위험이 있는지 평가해줘.
MVP 포함/제외 기준에 따라 유지, 보류, 폐기 중 하나로 판단해줘.

화면 디자인을 시킬 때

멍냥우편함은 피드 서비스가 아니라 아침 이메일 우편 경험이다.
화면이 앱 체류를 늘리는 방향이 아니라, 수신 신청/사진 업로드/반응 완료를 조용히 끝내는 방향인지 검토해줘.

구현을 시킬 때

AGENTS.md, MVP 범위, 정책과 검증 기준을 먼저 읽고 작업해줘.
댓글, 팔로우, 공개 피드, 랭킹, 무승인 실제 발송은 추가하지 마.
작업 후 검증 체크리스트와 남은 리스크를 보고해줘.

리뷰를 시킬 때

이 변경이 멍냥우편함의 정체성을 지키는지 리뷰해줘.
특히 SNS화, 이메일 스팸화, 무단 이미지, 개인정보, 사람 승인 누락 관점에서 봐줘.

7. 다음에 보강할 하네스

MVP 구현으로 넘어가기 전에 다음 문서를 추가하면 좋다.

  • `docs/email-template.md`: 실제 이메일 톤과 구성
  • `docs/admin-review.md`: 운영자 검토 화면과 판정 기준
  • `docs/data-model.md`: 사진, 발송, 반응, 신고 상태 모델
  • `docs/manual-test-checklist.md`: 출시 전 수동 테스트 체크리스트
  • `docs/failure-log.md`: 반복 실패와 재발 방지 규칙

8. 최종 정리

멍냥우편함의 하네스는 AI를 더 자유롭게 만들기 위한 장치가 아니다.

오히려 AI가 귀여운 사진 서비스의 흔한 길로 가지 않도록, 작은 우편 경험을 지키는 울타리다.

핵심은 하나다.

AI가 많이 만들게 하지 말고, 멍냥우편함답게 만들게 한다.
